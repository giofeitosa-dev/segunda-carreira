## Migração Flyway `V3__auditoria_seguranca.sql`

```sql
CREATE TABLE IF NOT EXISTS auditoria_seguranca (
    id            BIGINT NOT NULL GENERATED BY DEFAULT AS IDENTITY,
    usuario_id    BIGINT,
    acao          VARCHAR(100) NOT NULL,
    recurso       VARCHAR(500) NOT NULL,
    ip            VARCHAR(45) NOT NULL,
    data_hora     TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
    correlation_id VARCHAR(64) NOT NULL,
    CONSTRAINT pk_auditoria_seguranca PRIMARY KEY (id),
    CONSTRAINT fk_auditoria_usuario FOREIGN KEY (usuario_id) REFERENCES usuario (id) ON DELETE SET NULL
);
CREATE INDEX idx_auditoria_usuario ON auditoria_seguranca (usuario_id);
CREATE INDEX idx_auditoria_data_hora ON auditoria_seguranca (data_hora);
CREATE INDEX idx_auditoria_correlation ON auditoria_seguranca (correlation_id);
```

- H2 e PostgreSQL compatíveis (sem tipagens específicas de um SGBD).
- `ddl-auto=update` do prod continua como safety legado — a tabela nasce pelo Flyway (Constituição: Flyway é o mecanismo principal).

## Sem mudanças em entidades existentes

- `Usuario`, `Perfil`, etc. **não ganham colunas** — o vínculo com auditoria é apenas via `usuario_id` FK opcional.

## DTO de resposta: `AuditoriaResponse`

| Campo | Tipo | Observação |
|---|---|---|
| `id` | Long | identificador do registro |
| `usuarioId` | Long | nullable — usuário que executou a ação |
| `acao` | String | tipo de ação executada |
| `recurso` | String | caminho da API acessado |
| `ip` | String | IP do cliente |
| `dataHora` | LocalDateTime | momento do evento |
| `correlationId` | String | ID de correlação com logs/resposta |

## Estados do ciclo de vida do registro

```
[evento de segurança] → registro imutável em auditoria_seguranca (sem update/delete)
```

Não há exclusão de registros de auditoria neste ciclo (imutável por design).
